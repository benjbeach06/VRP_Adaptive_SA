===========================================

Companion to planning/raw-delta-accounting.md. TEMPORARY: delete once the refactor lands.

Purpose: a starting inventory so the implementing session does not re-derive the surface. Line

-------------------------------------------------------------------------------
0. THE LAYER MAP
-------------------------------------------------------------------------------

Four layers today. The refactor moves the boundary between 2 and 3.

  L1  raw quantity computation      travel_delta_if_*, load deltas          STAYS AS IS
  L2  derivation of accounting      activation / overload / depot usage     MOVES TO PROCESSOR
  L3  per-mutation aggregation      cost_deltas_if_*, cost_deltas_for_*     BECOMES RAW PRODUCER
  L4  mutation + inline bookkeeping core model mutators                     BOOKKEEPING STRIPPED

Counts: L1 ~26 methods, L2 ~29 methods, L3 24 methods, L4 ~44 accounting call sites.

The L2 methods are the duplicate work. Each L3 aggregator has to know which L2 methods its own
mutation needs; that per-site knowledge is what the processor centralizes.


-------------------------------------------------------------------------------
1. THE PROTOTYPE THAT ALREADY EXISTS  [VERIFIED]
-------------------------------------------------------------------------------

Route.depot_activation_delta_from_depot_num_usage_deltas          (static, ~1605)

    Signature: (depot_usage_deltas: defaultdict[Depot, int],
                depot_route_starts: defaultdict[Depot, RouteSet]) -> int

This is the refactor in miniature, for depots only: count deltas plus current state, resolved to
an activation delta. It reads len(depot_route_starts[depot]) to decide whether a usage change
crosses the zero boundary.

The processor generalizes this one function to vehicles, routes, and overload. Start here; the
signature shape (raw count deltas + current aggregate state -> resolved transitions) is the
contract for the whole processor.

Also verified nearby: the comment at ~601 distinguishing the USAGE-COUNT question from the
ACTIVATION question, and warning that gating on the wrong one leaves depot_route_starts
permanently too high. That distinction is exactly the num_use vs is_used split the refactor
formalizes.

6. NEW CODE
-------------------------------------------------------------------------------

6a. The raw delta record
    Fields, per the agreed design (transition form where a step function needs the base):
      route travel distance        delta      (adds; no base needed)
      route load                   (init, final)
      route customer count         (init, final)
      route start depot            (init, final)
      route -> vehicle assignment  (init, final)   UNASSIGNED sentinel covers create and dispose

    Composition: distance adds; the four transition fields chain on the route key and DROP when
    init == final. One merge operator, not five.

6b. The processor  (static, home undecided -- core_model for now is acceptable)
    raw record + FullSolution aggregate state -> (ObjectiveTermDelta, accounting record)
    Generalize depot_activation_delta_from_depot_num_usage_deltas (section 1) to all four
    aggregates: depot uses, vehicle active routes, route activity, vehicle overload.

6c. ObjectiveTermDelta  ~169  [VERIFIED]
    Already a NamedTuple with __pos__, __neg__, __add__, __sub__, get_cost_delta. Extends
    cleanly.

    WARNING: all five fields have defaults (= 0). tests/_harness.py term_deltas() constructs it
    with explicit keyword arguments, so a NEW FIELD WITH A DEFAULT is silently skipped by every
    per-term assertion in the contract suite. Give new fields no default, or update term_deltas()
    in the same commit.

7. OPERATOR LAYER
-------------------------------------------------------------------------------

7a. OperatorBL  (SimAnn_VRP_BLOperators.py ~92)  [VERIFIED]
    The base class already owns evaluate / apply / revert / commit with version gatekeeping. The
    three bookkeeping calls go in the DRIVERS, once, covering all 11 subclasses:

      evaluate ~160   raw record -> processor -> ObjectiveTermDelta; store both on the Move
      apply    ~199   after _apply_impl, hand the accounting record to FullSolution
      revert   ~229   after _revert_impl, hand back the inverse

    Move (~47) is a frozen dataclass carrying `deltas: ObjectiveTermDelta`. It needs the raw
    record too, or the accounting record. Only already_applied is mutable, via mark_applied().
    Adding a field means extending the frozen dataclass, not mutating it later.

    commit() ~252 has TODO(undo-stack) proposing to push (self, _revert_info, move.deltas). The
    accounting record is what that stack actually wants. Worth resolving together.

7b. Subclass hooks: _evaluate_impl returns raw, not ObjectiveTermDelta
    11 subclasses, all in SimAnn_VRP_BLOperators.py:
      ReassignRouteBefore ~270, ReassignCustomerChain ~305,
      ReassignCustomerToNewRouteBefore ~365, SwapCustomerChains ~408,
      ReverseCustomerChain ~472, PermuteChain ~502, ChangeEndDepot ~551,
      DisposeOfEmptyRoutesBL ~574, SplitRoute ~627, CombineRoutes ~655,
      _SequentialCombineRoutes ~704

    Most _evaluate_impl bodies are one call into an L3 aggregator plus validity guards
    (ReassignRouteBefore verified: guards, then cost_deltas_if_inserted_before). If that holds
    across all 11, the subclass diff is small and mechanical.

    _evaluates_by_applying operators mutate during evaluate. They read objective_terms() before
    and after rather than pricing predictively, so they need explicit handling: the processor
    contract assumes an unmutated base.

    _SequentialCombineRoutes is the existing sequential case. It is the first real test of the
    composition rule and should be converted early, not last.

7c. SimAnn_VRP_Operators.py -- 20 operators over the lifecycle, plus operand selection.
    NOT INVENTORIED. Predicted low impact: the accounting primitives grep found zero hits in this
    file. Confirm before planning the diff.

9. OPEN QUESTIONS FOR THE IMPLEMENTING SESSION
-------------------------------------------------------------------------------

1. End-depot usage. Two L2 methods return end-depot usage deltas, but end-depot use is not an
   objective term and the code that wrote it into depot_route_starts is dead-commented (~984).
   Decide whether the raw schema carries end-depot transitions before writing it.

2. _evaluates_by_applying operators. They price by mutating, so there is no unmutated base for
   the processor to read. Needs an explicit contract.

3. Where the processor lives. Agreed as not a design question for this plan. core_model is fine
   initially; module-structure.md is deliberately deferred and must not get dragged in.

4. Does Move carry the raw record, the accounting record, or both? Interacts with
   TODO(undo-stack) in commit().

5. SimAnn_VRP_Operators.py (20 operators) is uninventoried. Confirm zero accounting there.
