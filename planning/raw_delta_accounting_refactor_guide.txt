-------------------------------------------------------------------------------
0-BIS. WHICH STEP TOUCHES WHAT
-------------------------------------------------------------------------------

The rollout is staged PER OBJECTIVE TERM. ObjectiveTermDelta is a 5-field NamedTuple that adds
componentwise, so a term can be produced by the old path or the new one and the sum stays correct,
as long as exactly one side produces each term. The L3 aggregators return both delta types side by
side until the last term has moved.

  step 0  plumbing        record + stub processor + dual return + the two missing oracles (8a-bis)
                          NO BEHAVIOR CHANGE. Gate is a bit-identical deterministic run.
  step 1  travel_distance identity derivation. Strips no cache. Proves the processor path.
  step 2  total_route_overload   hinge over the load transition. Strips no cache.
  step 3  depots_activated + vehicles_activated + vehicles_overloaded
                          THE BULK. All cache stripping happens here. Sections 2, 3, 5 apply.
  step 4  end-depot usage tracking   (question 1)
  step 5  cleanup         delete the dual return and every now-dead L2 method. Measure perf here.

WHY STEPS 1 AND 2 ARE FIRST: only 2 of the 5 terms have an incrementally-maintained DERIVED cache
-- depots_activated (depot_route_starts) and vehicles_overloaded (num_routes_overloaded).
travel_distance and total_route_overload are backed by RAW caches whose step functions are already
evaluated at read time, so only the derivation moves.

WHY STEP 3 IS INDIVISIBLE: its three terms all read the same two transitions -- route activity
(is_active = assigned AND path_len > 0) and route-to-vehicle assignment. One mutation updates all
three caches in a single body (unlink_from_vehicle ~2841, link_to_vehicle_before/_after
~2890/~2909). Converting one alone means deriving those transitions in the processor and in the
mutator at the same time: a temporary patch with no place in the final code.

Commit per step while working, then SQUASH. The side-by-side state is scaffolding, not history.

0. THE LAYER MAP
-------------------------------------------------------------------------------

Four layers today. The refactor moves the boundary between 2 and 3.

  L1  raw quantity computation      travel_delta_if_*, load deltas          STAYS AS IS
  L2  derivation of accounting      activation / overload / depot usage     MOVES TO PROCESSOR
  L3  per-mutation aggregation      cost_deltas_if_*, cost_deltas_for_*     BECOMES RAW PRODUCER
  L4  mutation + inline bookkeeping core model mutators                     BOOKKEEPING STRIPPED

Counts: L1 ~26 methods, L2 ~29 methods, L3 24 methods, L4 ~44 accounting call sites.

The L2 methods are the duplicate work. Each L3 aggregator has to know which L2 methods its own
mutation needs; that per-site knowledge is what the processor centralizes.

7. OPERATOR LAYER
-------------------------------------------------------------------------------

FOUR JOBS, FOUR HOMES, NO OVERLAP. This is the payoff of applying accounting in the wrapper:

    core model      REPORTS RAW. Structural transitions only. No step function, ever.
    processor       RESOLVES.    Raw record + current state -> ObjectiveTermDelta + accounting
                                 record. A DEDICATED CLASS IN ITS OWN FILE. THE ONLY PLACE A STEP
                                 FUNCTION IS EVALUATED. Reads state, writes nothing.
    Operator        APPLIES.     Drives the two Move bits and calls the sink. Four methods.
    FullSolution    IS THE SINK. The one call that writes a derived cache. Takes ALREADY-PROCESSED
                                 numbers and DECIDES NOTHING.

    (OperatorBL sits between core model and processor: it passes raw deltas up and runs the
    processor in evaluate. It no longer knows anything about accounting beyond carrying the
    record.)

DO NOT COLLAPSE THE PROCESSOR INTO FullSolution. It is tempting -- FullSolution already holds the
state the processor reads, so folding the resolution in looks like it saves a hop. It does not. It
puts step-function evaluation back INSIDE THE CORE MODEL, which is the dual truth this whole
refactor exists to remove, and it breaks the "core model must never import the processor" check by
making the processor part of the core model.

    THE CHECK: if the FullSolution apply call contains a threshold comparison or a zero-crossing
    test, the processing has leaked into the sink. It should be doing arithmetic on numbers that
    arrived already resolved.

Nothing in the 34 Operator subclasses changes. Nothing in the 11 OperatorBL subclasses gains
accounting logic; they only pass up what their L3 aggregator now returns.

7a. OperatorBL -- PRICING ONLY  (SimAnn_VRP_BLOperators.py:92 `class OperatorBL[Ops: tuple](ABC):`)
    The base class owns evaluate / apply / revert / commit with version gatekeeping. Exactly ONE
    driver changes, and it covers all 11 subclasses:

      evaluate  :160 `def evaluate(self, operands: Ops) -> Move[Ops]:`
                     unpack the dual return, run the processor, store both records on the Move.

    apply :199 and revert :229 do NOT touch accounting. See question 2 -- accounting is applied by
    the Operator WRAPPER, because OperatorBL.apply is unreachable for a by-applying move.

    Move :47 `class Move[Ops: tuple]:` is a frozen dataclass carrying `deltas: ObjectiveTermDelta`.
    It gains the raw record, the accounting record, and the accounting_applied bit. Only
    already_applied is mutable today, via mark_applied() :82; the new bit needs a parallel
    mark_accounting_applied(). Adding a field means extending the frozen dataclass, never mutating
    it later.

    commit() :252 `TODO(undo-stack)` proposes pushing (self, _revert_info, move.deltas). LEAVE IT
    OPEN. That feature wants the full information to revert a CHAIN of moves; the accounting record
    is accounting-undo information only -- better than the bare ObjectiveTermDelta the TODO names,
    but not what the undo stack needs. Out of scope for this refactor.

   Exactly two operators set it, and both are benign:

       PermuteChain              SimAnn_VRP_BLOperators.py:518  `_evaluates_by_applying = True`

       _SequentialCombineRoutes  SimAnn_VRP_BLOperators.py:743  `_evaluates_by_applying = True`

   THE CAVEAT, AND THE DESIGN THAT ANSWERS IT.

   A by-applying operator mutates during _evaluate_impl, so the structure moves before any apply
   call happens. Mutation and accounting are therefore SEPARATE EVENTS and need separate state.

   CORRECTION [2026-08-27]: an earlier draft of this section said the record is applied in
   OperatorBL.apply, and that stress.py and the solver already call apply() unconditionally so only
   the contract test needed changing. BOTH CLAIMS WERE WRONG. Callers drive the Operator WRAPPER,
   and the wrapper is what no-ops -- OperatorBL.apply is UNREACHABLE for a by-applying move through
   every caller, production and tests alike. Do not reinstate that design.

   THE DESIGN:
     * The PROCESSOR (dedicated class, own file) resolves the raw record against current state into
       an ObjectiveTermDelta plus an accounting record. Only it evaluates a step function.
     * FullSolution owns ONE central call that applies that ALREADY-PROCESSED record, propagating
       update handles down to its vehicles and routes. NOTHING ELSE WRITES A DERIVED CACHE, and

     * Operator.apply   : not applied      -> mutate, then apply accounting

     * Operator.revert  : undo accounting if accounted, THEN undo the move if applied.
